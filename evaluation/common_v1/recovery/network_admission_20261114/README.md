# 网络故障后的自动准入与接续

日期：2026-11-14。适用对象：同一1770注册首试队列（纯ASR＋π0.5为840例，ASR＋Agent Oracle辅助为930例）。原Ours930结果不改。

## 用户看到的状态意味着什么

|状态|含义|是否派发新案例|
|---|---|---|
|`running_auto_network_admission`|正常执行|是|
|`draining_after_error`|出现新错误，等待所有在途案例收尾|否|
|`network_health_admission`|在途项已收尾，独立检查域名及云端规划服务|否；通过后继续未开始项|
|`stopped`|未知故障、账户拒绝、健康检查未恢复或用户要求停止|否|
|`completed`|1770注册项都已结束；问答判分仍需另核对|否|

因此，`draining_after_error`不能解释为仍在正常连续派发，更不能把案例数增加解释为物理任务成功。

## 本次故障与已有记录

上一接续最终停在286/1770，无在途遗留。最近故障为`B1:T2:T2COL1_EM_G01:R01`：云端Qwen3.8-27B请求120秒读取超时。累计6个保护标记包括1个HTTP500、2个DNS失败、2个读取超时，以及1个T5等待澄清/收尾异常。不是286例都失败，不能直接将此数当物理失败数。

全部286份原结果和1770注册表均有哈希快照；剩余1484项尚未开始。原故障详见相邻的cloud500、dns及continuation266历史目录。

## 新增了什么

只改部署调度，不改冻结Actor、权重、提示词、音频、场景、动作种子、评分阈值或正式请求重试次数：

1. 新故障先停止新增派发，等待全部在途项结束。
2. 保存本轮故障原因与案例身份；原失败结果保留原位及固定分母。
3. 仅对已识别的网络错误及有严格证据的T5规划未返回收尾情况，执行独立健康检查。
4. 健康检查读取原不计入正式成绩的预检输入，按原01号Qwen3.8-27B、完整图像/文本及1800最大词元参数做最多四路调用；**不重问正式案例，不把健康检查回答用于正式动作或评分**。
5. 检查通过后只继续尚未开始的注册项，模型服务保持加载，避免每次重启七套模型。
6. 不明异常、评分错误、事实时间对齐不合格、账户1007/401/403、模型身份改变均停止，不能靠自动重试掩盖。

每次最多3轮独立健康检查，轮间等待30秒；最多32次故障恢复。正式案例内的模型请求仍不自动重发。用户可在部署根目录创建`STOP_AFTER_CURRENT`，或在本目录创建`STOP`，让在途项收尾后停止；明确停止不会自动恢复。

这是部署层故障恢复策略的新修订，原冻结方法本身未改。以前的中断与这版调度均需在论文/补充材料披露，不能声称整轮并发、网络和调度始终相同。所有首次结果保留，不按成功率挑选案例。

## 验证与边界

- 本地及240容器各13项检查通过。
- 包含一项完整模拟：保留286个旧结果，执行剩余1484个模拟项，中途故意让一个请求超时；确认失败项只执行一次，健康检查后接续，最终1770项齐全且原失败未被覆盖。
- 真实运行是否已经开始/推进，以`STATUS.json`和本目录`LIVE_CHECK.json`时间为准；模拟测试不算正式1770成绩。
- 原冻结源文件、七卡映射、权重及归一化身份继续核验。
- 原容器DNS修复沿用，宿主机DNS未改；这不等于解决了云服务内部慢请求。
