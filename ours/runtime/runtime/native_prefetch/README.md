# C3r原生动作提前推理候选

显式入口 `service_recovery.py`。它继续载入原C3r recovery、R7-T3.2生命周期与R8语音；仅用一个混入类恢复此前T1的原生提前推理机制，不替换Symbolic规划器、M1、YOLO、动作权重、提示词或最终完成判断。

问题证据：固定S15十例首轮中，NativeCompleteTask在四步队列完全耗尽后才请求下一次预测，推理期间额外执行保持步；此前T1的NativeRealtimePrefetch在队列尚有动作时提前请求。代码差异及逐物理帧记录可以核对。该差异是需要验证的执行因素，不能仅凭单例失败就证明全部因果。

方法：保留10步预测，按物理帧差选择四步，在四步边界提交；不增加每次执行步数，不重播过期动作，不暂停物理时钟。超过预测覆盖范围时停止并报告，暂停/换任务使旧结果失效。

原Native子类的`_finish`和采集时钟覆盖保留，C3r当前契约的释放/支撑/稳定/保持终验仍是唯一完成出口。候选状态标注`native_scheduler=prefetch-frame-aligned-v1`，服务版本`R7-T3.2+C3r+NativePrefetch-v1`。冻结父包不修改，现有8787/T8/其他分支不会因此自动迁移。

无动作回归：`test_scheduler.py`。真实验证必须另开整轮、固定原十音频与初始化，不从不同轮拼成功案例。
